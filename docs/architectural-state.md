# Architectural-state enumeration

The state definitions in libhw are not a curated list of registers that looks
complete. They are generated by walking every register table of a pinned,
authoritative manual and recording an explicit decision for every row. CI fails
if a row is left unaccounted for, if a table appears that nobody has reviewed,
or if the generated tables drift from the manifests.

## What is claimed

> Every register the ARMv7-M Architecture Reference Manual lists in its own
> register index, plus every row of every register-summary table in the
> Cortex-M7 r0p2 Technical Reference Manual, is either represented by libhw or
> explicitly classified with a reason.

That claim is checked mechanically. It is not a claim about SoC peripherals,
which are a separate layer and are deliberately out of scope.

## Namespaces

State is kept in separate universes so that the meaning of a "CPU snapshot"
does not drift with how many peripherals a given TRM happens to document.

| Namespace | Holds |
|---|---|
| `HW_NS_ARCH` | ISA-defined PE state |
| `HW_NS_CPU` | implementation-defined state of one CPU revision |
| `HW_NS_DEBUG` | CoreSight, DWT, ITM, FPB, CTI, ROM tables |
| `HW_NS_CLUSTER` | SCU, private timers, GIC CPU interface (unused on Cortex-M) |
| `HW_NS_UNDOCUMENTED_DISCOVERED` | found experimentally; never counted as documented |

On Cortex-M7 the CPU-specific set is exactly the ten registers the TRM adds:
`CM7_ITCMCR`, `CM7_DTCMCR`, `CM7_AHBPCR`, `CM7_CACR`, `CM7_AHBSCR`,
`CM7_ABFSR`, `IEBR0/1`, `DEBR0/1`. Everything else the TRM prints is either
architectural (classified `architecture_defined`) or debug-block state.

## Pipeline

```
pinned manual (SHA-256)
        |
        v  tools/state_tables.py   reviewed keep/skip decision per table
spec/rules/<target>.tables.yaml
        |
        v  tools/state_import.py   row profiles, classification, crosscheck
spec/arm/<target>.yaml             normalized manifest with provenance
        |
        v  tools/state_gen.py
generated/<target>.def             consumed by core/hw_state.c
build/state-coverage/<target>.json
```

`.def` files are outputs. To change what state libhw knows about, change the
rules the importer reads and re-import; never edit a `.def` by hand.

## Why each stage refuses to guess

**Sources are pinned by SHA-256** (`spec/sources.lock.yaml`). The importer
refuses to run against a document whose bytes do not match. The Arm manuals are
licensed and are not redistributed here; the lock records their identity so any
machine holding a legitimate copy can prove it is working from the same bytes.
Set `HW_SPEC_SOURCE_DIR` to point at them.

**Every table caption gets a reviewed decision.** 220 captions across the two
documents, each marked keep or skip with a reason
(`spec/rules/*.tables.yaml`). If a revised manual introduces a table nobody has
decided on, `make state-check` fails rather than quietly ignoring it. There is
no generic `IGNORE`: an exclusion without a reason is rejected.

**The manual checks itself.** DDI0403E.e publishes its own register index
(Tables D8-2 and D8-3). The importer parses those indexes and asserts that every
name in them is present in the manifest. This is what caught the 32 registers
missing from an earlier draft of the rules -- the CPUID feature ID registers,
the cache and branch-predictor maintenance operations, and the CFSR
sub-registers. Both indexes now report 65/65 and 28/28.

**Encodings are checked against an independent assembler.** A complete list with
wrong encodings is useless, so the `SYSm` values read out of Table B5-1 are
compared with what `llvm-mc` emits for `mrs r0, <reg>` (14 checked, 14 agree).
The assembler is an encoding oracle, never a completeness authority.

**CMSIS is a cross-check, not the source.** `tools/state_cmsis_diff.py` compares
the manifest against a CMSIS-Core header by absolute address, because CMSIS
names fields relative to a block (`SysTick->CTRL`) while the manuals use global
names (`SYST_CSR`). Differences are reported for investigation and never
auto-resolved. It has already caught two real bugs in this importer.

### Known, explained differences from CMSIS

| Difference | Explanation |
|---|---|
| `NVIC->IP[n]` (240 bytes) vs `NVIC_IPRn` (60 words) | Same storage, different access granularity. A view, not extra state. |
| CoreSight ID/lock registers per block (`ITM->PID4`, `DWT->LAR`) | The architecture defines these generically for all CoreSight components (Appendix D1); CMSIS instantiates them per block. The Cortex-M7 overlay does enumerate them per component. |
| `DWT->COMP1..3` | The architecture models comparators as a runtime-sized array (`n = 0..DWT_CTRL.NUMCOMP-1`); CMSIS fixes a count. |

## Conditional state

Registers whose presence or count is not fixed by the architecture carry a
`feature_requirement` resolved against `spec/arm/armv7m.features.yaml`:
`FP_EXTENSION`, `MPU`, and `IMPDEF:DWT_CTRL.NUMCOMP`. The DWT comparator
registers are modelled as one conditional array rather than an invented fixed
expansion, because the architecture genuinely does not fix the count.

## Two encodings for the same state

A register reachable both by instruction and by debugger has two different
encodings, and conflating them reads the wrong thing:

| State | MRS/MSR `SYSm` (Table B5-1) | DCRSR `REGSEL` (C1.6.3) |
|---|---|---|
| `MSP` | 8 | 17 |
| `PSP` | 9 | 18 |
| `PRIMASK` | 16 | 20, bits[7:0] |
| `BASEPRI` | 17 | 20, bits[15:8] |
| `CONTROL` | 20 | 20, bits[31:24] |

`SYSm` comes from a table and is checked against `llvm-mc`. `REGSEL` is given
as a prose field description, so it is transcribed by hand in
`spec/rules/armv7m.access.yaml`, flagged `extraction: manual`, and carries the
section and field it came from. A CI test asserts the two really do differ, so
nobody later "simplifies" them into one number.

## Validated on hardware

Run against an STM32F429I board over ST-LINK/V2.1 (`make && ./out/state_probe stlink`):

```
CPUID              0x410FC241  (PARTNO 0xC24)
Part               not recognised
CPU overlay        none pinned - architecture manifest only
FP extension       implemented
MPU regions        8
DWT comparators    4
NVIC INTLINESNUM   2  (96 interrupt lines)

armv7m (DDI0403 E.e): 610 state elements
  write-only (not sampled)    3
  AVAILABLE                 586
  BACKEND_UNSUPPORTED        21
```

The derived features match the part: 8 MPU regions, 4 DWT comparators and 96
interrupt lines are what an STM32F429 implements. Core and special-purpose
registers read through DCRSR/DCRDR return coherent values -- `XPSR=0x01000000`
with the T bit set, `MSP` in SRAM, `PC` in flash, `DHCSR` showing halted with
`S_REGRDY`.

PARTNO 0xC24 is a Cortex-M4. We hold no TRM for it, so the probe applies the
architecture manifest only and says so, rather than applying the Cortex-M7
overlay to a part it does not describe.

### What AVAILABLE does and does not mean

`AVAILABLE` means the read transaction completed, not that the register is
implemented. On Cortex-M an unimplemented word in the PPB generally reads as
zero rather than faulting, so a clean read is weak evidence of existence.
Runtime inaccessibility is reported separately from architectural absence, and
neither is inferred from the other.

This distinction caught a real defect. Eighteen ROM-table and CoreSight
registers are given in the manual as offsets within a component
(`0x000`, `0xFCC`, ...). They were being read as absolute addresses, which on
this part lands in boot-aliased memory -- so all eighteen read back cleanly and
were reported `AVAILABLE`. Encodings now record whether they are absolute or
relative, `hw_state_read` refuses a relative one, and a CI test keeps them
marked.

## Not done

Honest scope boundaries, so nobody mistakes silence for coverage:

- **AArch64 / ARMv9-A (AARCHMRS).** Not started. The machine-readable spec is
  behind a click-through licence on developer.arm.com and cannot be fetched
  automatically. The importer layout anticipates it, but no code claims it.
- **ARMv7-A / Cortex-A9.** Not started, for the same reason: DDI0406C.d and
  DDI0407 are not available here. The task spec's suggested first target was
  Cortex-A9 r4p1; ARMv7-M/Cortex-M7 was chosen instead because those manuals are
  available *and* match the hardware libhw actually drives through its stlink
  backend.
- **RISC-V.** `csrs.csv` from riscv-opcodes has been fetched and is pinnable, but
  no importer exists yet.
- **Component base addresses.** Eighteen ROM-table and CoreSight registers are
  documented as offsets within a component. No base addresses are recorded, so
  `hw_state_read` refuses them rather than guessing. Recording the bases would
  make them readable.
- **CPU overlays beyond Cortex-M7.** Only DDI0489B is pinned, so PARTNO 0xC24
  (Cortex-M4, the part on the bench) gets architecture-only coverage. Adding it
  is a matter of pinning DDI0439 and writing a rules file -- no new methodology.
- **Snapshot serialization (§34).** The snapshot set is computed and CI asserts
  the generated set matches the manifest, but there is no serializer.
- **Write paths.** Everything here reads. Nothing writes architectural state
  apart from DCRSR, which is how a debugger selects a register for transfer.
